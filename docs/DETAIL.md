# 轻量会话窗口

打开或翻看会话时，只把「最近两轮」历史整段加载进来，更早的内容折叠在原有的「加载更早」按钮后面，滚动到顶部或点击大纲跳转时才一页页取回。

## 为什么按 Turn 而不是按消息数

原来的首屏预算是 `maxMessages: 500`、`turnWindow: { minMessages: 50, minTurns: 2 }`：只要满 50 条消息并跨过 2 个 Turn 就停。问题是这个规则会在 Turn 中间切断——一轮很长的对话（几十次工具调用）可能只露出后半截，读起来是断的。

所以这里的预算改成「按 Turn 收口」，并且**不压缩当前轮**：

| 请求 | 原预算 | 本插件预算 |
| --- | --- | --- |
| 打开会话 / 重连 | 最多 500 条，至少 50 条且跨 2 个 Turn | 最近 **2 个 Turn**（`minTurns: 3`），最多 500 条 |
| 向上翻页 / 跳转 | 最多 500 条，至少 50 条且跨 2 个 Turn | 每页 **2 个 Turn**（`minTurns: 3`），最多 400 条 |

`minTurns` 数的是从最新一条往回扫到的 `turn/start` 边界个数，N 个边界就是 N-1 个完整 Turn。最近一轮永远完整保留，所以正在生成、正在看的那一轮不会被折叠；被折叠的是再往前的部分。

## 效果

在真实会话日志上模拟同一套分页规则（解压后的记录、按消息数与 Turn 边界切页）：

| 会话 | 全部内容 | 原规则首屏 | 本插件首屏 |
| --- | --- | --- | --- |
| 16 轮的 Recaf 会话 | 13.4 MB / 576 条 | 3.4 MB / 179 条 | 0.2 MB / 21 条 |
| 7 轮的 Ghidra 会话 | 7.8 MB / 417 条 | 1.0 MB / 69 条 | 3.4 MB / 192 条 |
| 2 轮的 subagent 会话 | 8.1 MB / 309 条 | 8.1 MB / 309 条 | 8.1 MB / 309 条 |

多轮长会话首屏能少一个数量级；只有一两轮的会话本来就撑不满一次分页，折叠无处可折，行为不变——这类会话的重量来自「一轮里塞了几百次工具调用」，不属于历史折叠能解决的问题。个别轮次特别大的会话（如上表 Ghidra）按 Turn 收口会比按 50 条消息切更大，这是「当前轮不被切断」换来的代价，可以用下面的旋钮调回按消息切。

## 可调项

客户端 bundle 不接收插件配置，预算写在 `client.js` 顶部：

```js
const settings = {
  openingTurns: 3,       // 首屏保留 2 个 Turn（N-1）
  openingMaxMessages: 500,
  pageTurns: 3,          // 每次「加载更早」2 个 Turn
  pageMaxMessages: 400,
}
```

运行时也可以直接改：`window.__dshLiteWindow.settings.openingTurns = 2` 然后重新打开会话，无需重新构建。把 `openingTurns` 调到很大、`openingMaxMessages` 调到 500 以上，就回到接近原生的行为。

## 实现与边界

- 只装载在 Web 端，Node 侧无逻辑；不改会话数据、不改持久化、不改 Host 的请求预算。
- 预算装在会话历史流 `SessionEventStream.prototype.follow` / `readPage` 上，这两个方法来自 `@deepseek-ai/dsh-api-session-controller` 的客户端导出。DSH 升级后若导出形状变化，插件会安静地什么都不做（不报错、不阻断启动）。
- Host 侧分页始终包含请求的 `throughSeq`，所以缩小预算只抬高页的下界：最新一条消息、正在流式生成的回复、Turn 跳转的目标都不受影响。
- 已经被加载进内存的旧事件不会被卸载（客户端没有卸载接口），折叠的含义是「不再主动加载」。
- 同一页面重复加载（HMR）只会安装一层预算；停用插件会还原原始方法。
